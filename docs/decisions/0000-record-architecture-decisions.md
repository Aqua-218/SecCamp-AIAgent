# 0000. 設計判断を MADR 形式の決定記録として残す

[決定記録](README.md) / 0000

> **対象読者:** `docs/` に文書を追加する全員、設計判断の前提を再検討する人

## Status

Accepted (2026-08-12)

## 背景と課題

`docs/` 配下 5,614 行を検索した時点で、「検討したが採用しなかった案」への言及は実質存在しなかった。文書は全て、決定済みの構造を事実として説明する形になっている。

このため次の問題が起きている。

- 読者が判断の前提を再構成できない。`PathPattern` がなぜ `Exact` と `Prefix` の 2 種類だけなのかは、[パスモデル](../authority-core/paths.md)を読んでも「そう決まっている」以上のことが分からない。
- 前提が変わったときに、どの決定を見直すべきか特定できない。
- 同じ検討が繰り返される。一度却下した案が、却下理由が残っていないため再提案される。
- 文書全体が、あらゆる判断が自明であったかのように読める。実際の設計はトレードオフの連続であり、その痕跡が消えている状態は、内容が薄いという印象の主要因になっている。

判断材料は次のとおりである。

- 決定の理由は、その決定を説明する実装文書とは寿命が違う。実装が変わっても決定の背景は残す価値がある。
- 実装文書に「なぜ別案を採らなかったか」を全て書くと、型A の概念ページが読み物として成立しなくなる。
- 追記のコストが高い形式は運用されない。

## 検討した選択肢

1. **決定記録を作らない** — 各実装ページに「なぜ別案を採らなかったか」節を必須化する
2. **設計書に決定節を追加する** — [`docs/design/`](../design/README.md) の各ページ内に決定の一覧を持つ
3. **MADR 形式の独立した決定記録を持つ** — `docs/decisions/NNNN-<slug>.md`

### 決定記録を作らない

各実装ページに却下理由の節を足すだけなので、ファイルは増えない。

- 利点: 新しい文書型を導入せずに済む。決定と実装の説明が同じ場所にある。
- 欠点: 実装ページが改訂されるたびに却下理由が更新対象になり、古い判断が消える。複数の crate にまたがる決定（identity の非再利用など）を置く場所がない。
- **採用しなかった理由:** 却下理由の寿命は実装の寿命より長い。実装ページと同じ改訂サイクルに置くと、実装を書き換えた人が「もう関係ない」と判断して消してしまう。決定記録は追記のみで、過去の決定を書き換えないことに価値がある。

### 設計書に決定節を追加する

[設計書](../design/README.md)の各ページに決定の一覧表を持つ。

- 利点: 設計判断は本来 `design/` の管轄であり、置き場所として自然。
- 欠点: 設計書は現在「なぜこの構造にするか」を説明する読み物として機能しており、1 ページに複数の決定を詰めると、どの決定がいつ確定したのかが追えない。決定の Status（Accepted / Superseded）を個別に管理できない。
- **採用しなかった理由:** 決定は個別に覆る。1 ファイル 1 決定でなければ、ある決定だけを Superseded にして新しい ADR へ差し替える操作ができない。

## 決定

**[MADR](https://adr.github.io/madr/) 形式の独立した決定記録を `docs/decisions/` に置く。**

1 決定 1 ファイル、`NNNN-<slug>.md`、連番は再利用しない。骨格は [`docs/templates/decision.md`](../templates/decision.md) とする。

決め手は 2 点である。第一に、決定は個別に覆るため 1 ファイル 1 決定が要る。第二に、MADR の `検討した選択肢` 節は、却下した案を書かなければ形式として成立せず、書き落としを構造で防げる。他の 2 案はどちらも、却下理由を書かずに埋められてしまう。

## 結果

- `docs/` に文書型が 1 つ増える。[文書規約](../document-conventions.md)の型D として定義し、`scripts/ci/check-docs.sh` が必須節の存在を検査する。
- 既存の主要な設計判断は遡って ADR 化する。対象は[決定記録の索引](README.md)に列挙する。遡及分は当時の議論記録が無いため、実装とコメントから再構成した内容になる。再構成であることを各 ADR の `結果` 節に明記する。
- ADR は追記のみとする。内容が古くなった場合は編集せず、新しい ADR を書いて `Status` を `Superseded by` に変える。
- 実装ページから ADR への一方向リンクを張る。ADR から実装ページへも張るため、実装ページの名前を変えるときは ADR の `関連` も追随させる必要がある。
